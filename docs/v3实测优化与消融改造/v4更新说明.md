## 改动内容

### §2.1 全量复验闸

**问题**：轻量 compact 集（少量 case）通过即判 PASS，存在假通过。  
**改动**：轻量通过阈值（≥99.0% match_rate）后，引擎自动替换为最全 case 集（`.json.bak`/`.json.full`，行数最多优先）重跑一遍，finally 恢复原文件。全量结果写入 `validation_result_attempt_N.json` 的 `full_eval` 字段。

`_compute_loop_signal` 语义变更（`scripts/gates/branch_precision.py`）：
- `passed=True` + 有 `full_eval`：全量 100% → PASS；crash 或未满 → `CONTINUE/full_eval_regression`（继续 debug）
- `passed=False` + `mr≥99%` + 全量 100% → 推 near-success 过线为 PASS
- 连续 ≥2 轮全量无改善 → `STOP/nearly_success`（防噪声无限重试）
- 无全量集 / 闸关：维持旧行为（向后兼容）

**涉及文件**：`engine/validate_runner.py`、`scripts/gates/branch_precision.py`

### §2.2 KB 入库判据改全量

**问题**：轻量假通过的成功轨迹会污染知识库。  
**改动**：`_finalize_impl` 前置判断——`full_eval` 存在时，仅 `matched_ratio ≥ 0.95` 且不 crash 的轨迹才入库。旧产物（无 `full_eval`）沿用原判据。

**涉及文件**：`engine/knowledge_finalize.py`

### §2.5 KB 命中率追踪

**改动**：`spawn_diagnose_agent` 末尾检查注入给 agent 的 KB top_titles 中哪些被其 `final_response` 引用，结果追加到 `precision_tuning/kb_usage_trace.json`（字段：`injected_titles`、`cited_titles`、`citation_rate`）。

**涉及文件**：`engine/agent_backend.py`

### §3 消融 toggle 机制

所有 toggle 以 `ABLATE_` 为前缀的 env 变量控制，子进程自动继承，无需代码改动，详见下方消融实验说明。

| 变量 | 关闭的组件 | 落点 |
|---|---|---|
| `ABLATE_FULL_EVAL=1` | 全量复验闸 | `validate_runner._full_eval_enabled()` |
| `ABLATE_FORENSICS=1` | forensics 取证步 | `next_action._round_sequence` |
| `ABLATE_GATE_A=1` | audit (Gate-A) 步 | `next_action._round_sequence` |
| `ABLATE_LOOP_GUARD=1` | N6 退化早停 + nearly_success 防重试 | `next_action` + `branch_precision` |
| `ABLATE_ANTICHEAT=1` | 反作弊/AST/C++ 扫描（检测整关） | `scripts/gates/common.run_common` |
| `ABLATE_PROBE=1` | L5 插桩定位（Sub-step 2.6） | `engine/agent_backend._build_prompt` |
| `ABLATE_KB=1` | KB 轮序、注入和公共读写入口 | `next_action` + `precision_knowledge.py` |
| `ABLATE_RECOVERY=1` | baseline checkpoint、current_best、rollback、方向历史 | `next_action` + `agent_backend` |
| `ANTICHEAT_DETECT_ONLY=1` | 反作弊**阻断**（检测+记录保留） | `scripts/gates/common.run_common` |
| `ASCENDC_DEBUG_KB_READ_ONLY=1` | KB 写回（检索仍保留） | `knowledge_finalize` + `precision_knowledge.py` |

#### 消融在技术上如何屏蔽模块

消融不是"删代码"或"换分支"，而是在模块的**单一控制点**用 env 旗标短路其副作用，其余流程不变。四种屏蔽手法：

1. **轮序剔除（forensics / KB / audit）**：`_round_sequence(failure_type)` 是每轮 step 序列的唯一生成处。`ABLATE_FORENSICS=1` 同时移除 `forensics` 和依赖其报告的 `knowledge_search`，probe policy 不再读取旧 `forensics_report`，prompt 也禁止 Agent 复用或重建该报告；`ABLATE_KB=1` 单独移除 `knowledge_search`，并在 `precision_knowledge.py` 的 load/search/check/dump 公共入口硬短路；`ABLATE_GATE_A=1` 仅供 `debug_no_audit` 调试 profile 使用，不属于正式消融矩阵。

   `ABLATE_KB=1` 下 `kb_usage_trace.json` 仍会按 attempt 生成，但固定记录空
   retrieved/injected 集合并标 `ablation_disabled=true`；旧
   `knowledge_search_log.json` 不参与本轮统计。Agent 若仍声明 `kb_used_ids`，只会落入
   `declared_unknown_ids`，便于发现越权声明。

2. **判定短路（loopguard / fulleval）**：`ABLATE_LOOP_GUARD=1` 关闭 nearly-success、fp16 ceiling、harmful regression、stagnant direction、N6 退化早停及 480-turn 自适应软预算，只保留 600-turn hard cap、attempt cap 和 branch cap 等安全上限；`ABLATE_FULL_EVAL` 让 `_full_eval_enabled()` 返回 False，全量复验整段跳过，回落轻量口径。

3. **prompt + 独立源码审计（probe）**：`ABLATE_PROBE=1` 时 prompt 明确禁用插桩；Agent 返回后，引擎对 `kernel/` 中 `printf/AscendCPrintf/DumpTensor/DataDump` 等调用做 before/after 扫描，写 `probe_source_audit_attemptN.json`。若 skip policy 下出现新增持久化探针，终态为 `ablation_violation`，Agent 自报 `skipped` 不能覆盖源码证据。临时插入后又删除、或在总调用数不变时替换已有探针，仍不可观测，报告中必须保留这一限制。

4. **检测/阻断解耦（anticheat）**：反作弊有两个独立旗标，语义正交——
   - `ABLATE_ANTICHEAT=1`：engine 内完全不执行反作弊；任务结束后批处理仅以 out-of-band observer 扫描并写 `precision_tuning/anticheat_observer.json`，不写 `_anticheat.json`、不重建 `debug_status`、不影响执行。
   - `ANTICHEAT_DETECT_ONLY=1`：检测与 `cheat_history` 记录照常，但 success/failure 两种情况下均不改写 loop signal，也不把作弊警告注入下一轮 prompt。它是纯观察器，不改变 baseline 的行为轨迹。

> 设计要点：所有屏蔽点都在模块的单一收敛处，对其余事件流零侵入；产物结构（`validation_result` / `cheat_history` / `success_category` 等）在各 arm 下保持一致，故跨 arm 的产物可直接对比，这是消融实验可量化的前提。

`no_anticheat` 构建退出产物时还会显式忽略 task 目录中可能残留的旧
`_anticheat.json` / `cheat_history.json`，防止 reset/copy 后的陈旧检测结果反向改变
当前 arm 的终态分类。由于运行期没有 AST/反作弊证据，该 arm 的成功只记 objective
success，不会伪装为 `clean_kernel_success`；clean 口径必须来自独立 post-hoc observer。

### 缺陷修复（消融正确性）

- **`no_loopguard` 漏判修复**：`branch_precision._full_eval_continue_or_stop` 中两处 `nearly_success` STOP（全量复验连续无改善、全量无可定位失败样本）原未受 `ABLATE_LOOP_GUARD` 约束，导致 `no_loopguard` arm 仍会在该路径提前 STOP，无法体现"关闭循环防护"的消融语义。现统一加 `loop_guard_on` 守卫，关闭时两处均改判 `CONTINUE`，与 `_compute_loop_signal` 内 nearly_success STOP（`branch_precision.py:349`）的既有守卫对齐。
- **终态拆分**：新运行分别使用 `stopped_by_attempt_limit`、`stopped_by_branch_limit` 和 `stopped_by_budget`；`stopped_by_loop_limit` 仅为旧产物兼容，避免把不同停止机制混为同一统计项。
- **实验冻结**：正式对比应传 `--kb-read-only`，并用 `--fixed-provider-assignments <prior/provider_assignments.json>` 复用严格一致的 task→provider 映射；后者会从当前 key config 重建 mode-0600 env 文件，但不会按实时 quota 重映射。
- **`re.split` 收尾**：`branch_precision.py` 两处 `re.split(r"[:：]", line, 1)` 改为 `maxsplit=1` 关键字传参，消除 Python 3.14 DeprecationWarning（UT 警告归零）。

**涉及文件**：`scripts/gates/branch_precision.py`

## 消融实验

批跑脚本通过 `--ablate-profile <arm>` 统一控制消融。脚本内部将 profile 展开为对应 env 变量，经 `docker exec -e` 传入容器，引擎代码无需任何改动。

```bash
bash utils/run_ascendc_debug_batch_cc.sh \
  --task-dirs-file <task_dirs.txt> \
  --containers <c1,c2,c3,c4,c5> --npus <1,2,3,4,5> \
  --output <out_dir> \
  --ablate-profile <arm>
```

### V5 可用 arm

V4 历史实验曾分别运行 `no_forensics` 与 `no_probe`。V5 正式矩阵将二者
合并为 `no_diagnostic_evidence`，用于估计整套结构化诊断证据能力的联合净
效应。旧 profile 会拒绝启动，避免把不同实验语义静默混在一起。

| `--ablate-profile` | 关闭的组件 | 对应 env |
|---|---|---|
| `full`（默认） | 无，完整系统 | — |
| `no_fulleval` | 全量复验闸 | `ABLATE_FULL_EVAL=1` |
| `no_diagnostic_evidence` | forensics、依赖 forensics 的 KB search、L5 probe | `ABLATE_FORENSICS=1` `ABLATE_PROBE=1` |
| `no_loopguard` | 所有语义早停及 480-turn 软预算 | `ABLATE_LOOP_GUARD=1` |
| `no_anticheat` | engine 内反作弊检查 | `ABLATE_ANTICHEAT=1` |
| `no_kb` | KB 调度、prompt 注入及公共读写入口 | `ABLATE_KB=1` `KB_PATH=""` |
| `baseline` | forensics + KB + loopguard + Gate-A + fulleval + probe + recovery 全关，反作弊纯 detect-only | 上述开关组合 |

`debug_no_audit` 只用于工程诊断，不得作为论文正式 arm；旧名称 `no_audit` 会直接拒绝启动。

`no_diagnostic_evidence` 仍保留 `diagnose_and_fix`，Agent 可基于源码、编译日志
和运行日志修复；它只关闭结构化 forensics/probe 证据通道。该 arm 只能支持
“组合能力是否有净收益”的结论，不能拆分归因 forensics 或 probe 的单独贡献。

`no_fulleval` 当前只保证运行期不消费 full-eval。为避免 observer 反向影响 task，
批处理不会在同一 task 目录自动补跑全量复验；该 arm 的 full-eval 对照必须在实验结束后
复制终态 kernel 到独立目录再离线执行，并在报告中标为 post-hoc observer。

正式重复实验还应固定两个协变量：

```bash
--kb-path <isolated-kb-snapshot.json> --kb-read-only \
--provider-pool-config <keys.json> \
--fixed-provider-assignments <prior-run/provider_assignments.json>
```

### 示例：验证全量复验闸 ROI

```bash
# Arm A: 完整系统
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile full --output out_full ...

# Arm B: 关闭全量复验闸
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile no_fulleval --output out_no_fe ...
```

比较两组 `exit_artifacts` 中 `success_category=clean_kernel_success` 的数量即可量化贡献。

### 示例：量化反作弊板块作用

`baseline` 采用 detect-only（检测+记录但不阻断），与 `no_anticheat`（检测整关）形成对照：

```bash
# Arm A: baseline (反作弊 detect-only，带作弊的成功被放行但标记 cheat_or_invalid)
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile baseline --output out_base ...

# Arm B: no_anticheat (检测整关)
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile no_anticheat --output out_no_ac ...
```

baseline 组 `exit_artifacts` 中 `success_category=cheat_or_invalid` 的数量，即反作弊板块在完整系统中会拦截掉的"虚假成功"数——直接量化该板块对结果可信度的贡献。
