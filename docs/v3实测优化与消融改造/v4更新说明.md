## 改动内容

### §2.1 全量复验闸

**问题**：轻量 compact 集（少量 case）通过即判 PASS，存在假通过。  
**改动**：轻量通过阈值（≥99.0% match_rate）后，引擎自动替换为最全 case 集（`.json.bak`/`.json.full`，行数最多优先）重跑一遍，finally 恢复原文件。全量结果写入 `validation_result_attempt_N.json` 的 `full_eval` 字段。

`_compute_loop_signal` 语义变更（`scripts/gates/branch_precision.py`）：
- `passed=True` + 有 `full_eval`：全量 100% → PASS；crash 或未满 → `CONTINUE/full_eval_regression`（继续 debug）
- `passed=False` + `mr≥99%` + 全量 100% → 推 near-success 过线为 PASS
- 连续 ≥2 轮全量无改善 → `STOP/nearly_success`（防噪声无限重试）
- 无全量集 / 闸关：维持旧行为（向后兼容）

**涉及文件**：`engine/validate_runner.py`、`scripts/gates/branch_precision.py`

### §2.2 KB 入库判据改全量

**问题**：轻量假通过的成功轨迹会污染知识库。  
**改动**：`_finalize_impl` 前置判断——`full_eval` 存在时，仅 `matched_ratio ≥ 0.95` 且不 crash 的轨迹才入库。旧产物（无 `full_eval`）沿用原判据。

**涉及文件**：`engine/knowledge_finalize.py`

### §2.5 KB 命中率追踪

**改动**：`spawn_diagnose_agent` 末尾检查注入给 agent 的 KB top_titles 中哪些被其 `final_response` 引用，结果追加到 `precision_tuning/kb_usage_trace.json`（字段：`injected_titles`、`cited_titles`、`citation_rate`）。

**涉及文件**：`engine/agent_backend.py`

### §3 消融 toggle 机制

所有 toggle 以 `ABLATE_` 为前缀的 env 变量控制，子进程自动继承，无需代码改动，详见下方消融实验说明。

| 变量 | 关闭的组件 | 落点 |
|---|---|---|
| `ABLATE_FULL_EVAL=1` | 全量复验闸 | `validate_runner._full_eval_enabled()` |
| `ABLATE_FORENSICS=1` | forensics 取证步 | `next_action._round_sequence` |
| `ABLATE_GATE_A=1` | audit (Gate-A) 步 | `next_action._round_sequence` |
| `ABLATE_LOOP_GUARD=1` | N6 退化早停 + nearly_success 防重试 | `next_action` + `branch_precision` |
| `ABLATE_ANTICHEAT=1` | 反作弊/AST/C++ 扫描（检测整关） | `scripts/gates/common.run_common` |
| `ABLATE_PROBE=1` | L5 插桩定位（Sub-step 2.6） | `engine/agent_backend._build_prompt` |
| `ANTICHEAT_DETECT_ONLY=1` | 反作弊**阻断**（检测+记录保留） | `scripts/gates/common.run_common` |

#### 消融在技术上如何屏蔽模块

消融不是"删代码"或"换分支"，而是在模块的**单一控制点**用 env 旗标短路其副作用，其余流程不变。四种屏蔽手法：

1. **轮序剔除（forensics / audit）**：`_round_sequence(failure_type)` 是每轮 step 序列的唯一生成处。读到 `ABLATE_FORENSICS=1` / `ABLATE_GATE_A=1` 时，把对应 step 名从精度轮序 `(forensics, knowledge_search, audit, diagnose_and_fix, validate)` 中过滤掉，引擎按裁剪后的序列派发——该 step 的 py_action 根本不会被调用，下游对其产物的读取走既有的"缺失即降级"兜底（如 forensics_data=None 时 `_compute_loop_signal` 仍能判定）。

2. **判定短路（loopguard / fulleval）**：`branch_precision._compute_loop_signal` 与 `_full_eval_continue_or_stop` 在产出 `STOP/nearly_success` 前检查 `ABLATE_LOOP_GUARD`，命中则把该 STOP 改写为 `CONTINUE`，让流程续跑至 `max_attempts_reached` 硬顶（有界，不死循环）；`ABLATE_FULL_EVAL` 则让 `_full_eval_enabled()` 返 False，全量复验整段跳过，回落 v3 轻量口径。两者都只改"是否触发某条收敛规则"，不动数值判定本身。

3. **prompt 注入（probe）**：L5 插桩是 agent 侧的 prompt 步骤（SKILL.md Sub-step 2.6），无对应引擎 py_action。`ABLATE_PROBE=1` 时 `_build_prompt` 在单轮约束层末尾追加一段覆盖指令，要求 agent 跳过插桩、`[L5_PROBE]` section 写"消融跳过"版（复用 SKILL.md 既有跳过口径，section 仍存在，不触发 Gate-A 缺失校验）。引擎侧的 probe 引用仅为统计透传（`l5_probe_degraded` / `l5_probe_source`），关插桩不影响引擎运行。

4. **检测/阻断解耦（anticheat）**：反作弊有两个独立旗标，语义正交——
   - `ABLATE_ANTICHEAT=1`：`run_common` 跳过 `check_anticheat` / `check_ast_degrade` / `check_cpp_regression` 整段，零检测、零开销，用于"完全无反作弊"基线。
   - `ANTICHEAT_DETECT_ONLY=1`：检测与 `cheat_history` 记录照常，仅在 `success + 作弊 → STOP cheat_detected` 这一**运行期阻断**点短路——带作弊的成功被放行（计入 `objective_success`），但 `exit_artifacts` 仍据 `cheat_history` 标 `success_category=cheat_or_invalid`。如此假阳性可见，与 `no_anticheat` arm 对比即可量化反作弊板块拦截了多少虚假成功。这是 `baseline` 的反作弊口径：消融的是阻断作用，而非检测能力。

> 设计要点：所有屏蔽点都在模块的单一收敛处，对其余事件流零侵入；产物结构（`validation_result` / `cheat_history` / `success_category` 等）在各 arm 下保持一致，故跨 arm 的产物可直接对比，这是消融实验可量化的前提。

### 缺陷修复（消融正确性）

- **`no_loopguard` 漏判修复**：`branch_precision._full_eval_continue_or_stop` 中两处 `nearly_success` STOP（全量复验连续无改善、全量无可定位失败样本）原未受 `ABLATE_LOOP_GUARD` 约束，导致 `no_loopguard` arm 仍会在该路径提前 STOP，无法体现"关闭循环防护"的消融语义。现统一加 `loop_guard_on` 守卫，关闭时两处均改判 `CONTINUE`，与 `_compute_loop_signal` 内 nearly_success STOP（`branch_precision.py:349`）的既有守卫对齐。
- **`re.split` 收尾**：`branch_precision.py` 两处 `re.split(r"[:：]", line, 1)` 改为 `maxsplit=1` 关键字传参，消除 Python 3.14 DeprecationWarning（UT 警告归零）。

**涉及文件**：`scripts/gates/branch_precision.py`

## 消融实验

批跑脚本通过 `--ablate-profile <arm>` 统一控制消融。脚本内部将 profile 展开为对应 env 变量，经 `docker exec -e` 传入容器，引擎代码无需任何改动。

```bash
bash utils/run_ascendc_debug_batch_cc.sh \
  --task-manifest <manifest.json> \
  --output-dir <out_dir> \
  --ablate-profile <arm>
```

### 可用 arm

| `--ablate-profile` | 关闭的组件 | 对应 env |
|---|---|---|
| `full`（默认） | 无，完整系统 | — |
| `no_fulleval` | 全量复验闸 | `ABLATE_FULL_EVAL=1` |
| `no_forensics` | forensics 取证步 | `ABLATE_FORENSICS=1` |
| `no_audit` | audit / Gate-A 步 | `ABLATE_GATE_A=1` |
| `no_loopguard` | 退化早停 + nearly_success 防重试 | `ABLATE_LOOP_GUARD=1` |
| `no_anticheat` | 反作弊检查（检测整关） | `ABLATE_ANTICHEAT=1` |
| `no_kb` | 知识库注入 | `KB_PATH=""` |
| `no_probe` | L5 插桩定位 | `ABLATE_PROBE=1` |
| `baseline` | forensics + loopguard + Gate-A + fulleval + probe 全关 + KB 清空 + 反作弊 detect-only | `ABLATE_FORENSICS=1` `ABLATE_LOOP_GUARD=1` `ABLATE_GATE_A=1` `ABLATE_FULL_EVAL=1` `ABLATE_PROBE=1` `ANTICHEAT_DETECT_ONLY=1` `KB_PATH=""` |

### 示例：验证全量复验闸 ROI

```bash
# Arm A: 完整系统
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile full   --output-dir out_full   ...

# Arm B: 关闭全量复验闸
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile no_fulleval --output-dir out_no_fe ...
```

比较两组 `exit_artifacts` 中 `success_category=clean_kernel_success` 的数量即可量化贡献。

### 示例：量化反作弊板块作用

`baseline` 采用 detect-only（检测+记录但不阻断），与 `no_anticheat`（检测整关）形成对照：

```bash
# Arm A: baseline (反作弊 detect-only，带作弊的成功被放行但标记 cheat_or_invalid)
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile baseline     --output-dir out_base ...

# Arm B: no_anticheat (检测整关)
bash utils/run_ascendc_debug_batch_cc.sh --ablate-profile no_anticheat --output-dir out_no_ac ...
```

baseline 组 `exit_artifacts` 中 `success_category=cheat_or_invalid` 的数量，即反作弊板块在完整系统中会拦截掉的"虚假成功"数——直接量化该板块对结果可信度的贡献。
